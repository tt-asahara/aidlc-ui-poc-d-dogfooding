# チームプラクティス

## Way of Working

私たちはトランクベース開発を採用します。このリポジトリではトランクを `setup/aidlc-d` とし、`main` ブランチは作成も変更もしません。すべての作業は `setup/aidlc-d` から切った短命な作業ブランチ（目安 1〜2 日以内に解決）で行い、成果は `setup/aidlc-d` にまとめます。長命ブランチは作りません。

- Construction のワークツリーは、ベースブランチ `setup/aidlc-d`、マージ先 `setup/aidlc-d` とします。
- Bolt ブランチは `setup/aidlc-d` へ squash マージします。1 Bolt = `setup/aidlc-d` 上の 1 コミットとし、コミット名は Bolt スラッグに合わせます。途中のコミット履歴はワークツリー破棄までソースブランチに残り、イベントの全履歴は監査ログで追跡します。
- 共通データ契約（データ型・CSV 形式などの契約）を先に定め、それに依存する Unit を依存順に進めます。
- 今回の進め方（恒久ルールではありません）: 今回の初回実行は比較用ベースラインとして公式の直列実行で進めます（並列化は使いません）。

## Walking Skeleton

最初に薄いエンドツーエンドの一本道（ウォーキングスケルトン）を作る儀式は行いません（`skeleton: off`）。

- スケルトン用のブートストラップチェックポイントは設けず、Construction 開始時に進め方（各チェックポイントでレビューするか、自動で続行するか）の明示的な選択を受けます。
- 最初の Unit は共通データ契約とし、以降の Unit はその依存順に進めます。共通データ契約はスケルトンの代替ではなく、Unit の依存順序として扱います。
- Plan Approval、検証コマンドの選択、失敗時は常に人間の判断で止まります。

## Testing Posture

テストはすべての Bolt における第一級の成果物として扱います。

- **Methodology**: custom
- **Methodology evidence**: ヒアリング Q3 で混合方式（C）が選ばれました。共通データ契約と CSV 変換は契約を先に固めるためテストを先に書き、画面などの UI は試行錯誤を妨げないよう実装後にテストを書きます。テストを書く時期がレイヤーによって異なるため `custom` とします。
- **Ordering**: 共通データ契約と CSV 変換のレイヤーはテストを先に書いて失敗を確認してから実装し、UI とその他のレイヤーは各レイヤーを実装した後にそのレイヤーのテストを書いて実行します。
- カバレッジ下限: 行カバレッジ 80% 以上を満たします。Build and Test はこの下限を検証し、通すために下限を下げることはしません。
- マージ前検証: lint・型チェック・テスト・カバレッジ（行 80% 下限）を一括で実行するローカルの単一コマンドを、マージ前に必ず実行して成功させ、その結果を記録します。外部の CI サービスは使いません。
- テスト戦略（量と種類）はアクティブな Test Strategy に従い、上記の下限はそれに追加されるもので、置き換えるものではありません。
- 必須のテスト観点: 入力エラー、空データ、読み込み中、保存失敗、キーボード操作を、該当する Unit のテストケースとして必ず含めます。
- テストデータは架空（合成）データのみを使います。
- テストランナーなどの具体的なツールは、要件・設計段階で決めます。

## Deployment

デプロイは行いません。ローカルでビルド・起動して確認できる Web アプリをゴールとします。

- ステージング／本番環境へのデプロイ、静的ホスティング等への公開は行いません。
- 外部サーバー・サービスへのデータ送信は行いません。
- 完了の確認は、ローカルでのビルドと起動、およびマージ前検証コマンドの成功で行います。

## Code Style

TypeScript を使い、プロジェクトのフォーマッター／リンター設定に従います。

- 型チェック: TypeScript の `strict` モードを有効にします。
- フォーマッター: Prettier（リポジトリ直下の設定ファイルで構成）。
- リンター: ESLint（TypeScript 対応設定）。
- フォーマット・lint・型チェックのいずれかが失敗した場合はマージしません。これらはマージ前検証コマンドに含めます。
- 命名規則: TypeScript の慣用（変数・関数は camelCase、型・コンポーネントは PascalCase）。プロジェクト独自の命名ルールは設けません。
- エージェントがコードスタイルを提案するときは、まずプロジェクトのリンター設定を読み、リンターが既にカバーしていない場合に限って提案します。
- UI フレームワークやビルドツールの選定は、要件分析・設計ステージで決めます。
