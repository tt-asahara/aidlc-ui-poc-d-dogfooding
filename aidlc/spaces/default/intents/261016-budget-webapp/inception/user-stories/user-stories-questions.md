# User Stories — ストーリー計画と質問

## 計画の概要

- **ペルソナ**: requirements.md の想定 A1（1人の利用者が自分のブラウザで使う）を出発点に、利用場面の違いを表すペルソナを作る（Q1 で決定）。
- **ストーリーの書式**: 「〔ペルソナ〕として、〔したいこと〕をしたい。それは〔得られる価値〕のためだ。」とし、INVEST（独立・交渉可能・価値がある・見積もれる・小さい・テストできる）を満たす。受け入れ条件は Given/When/Then。
- **ID**: ストーリーは `US{群}.{連番}`、受け入れ条件は `AC{群}.{連番}.{条件番号}`。requirements.md の FR・NFR すべてを traceability.json で対応づける。
- **優先度**: MoSCoW（Must / Should / Could / Won't）。最終的な範囲は Delivery Planning で決める（Q4 で方針を決定）。
- **分け方**: Q2 で決定。
- **粒度**: Q3 で決定。

## Q1. ペルソナの数

利用者は1人ですが、使う場面によって求めるものが違います。ペルソナの分け方で、ストーリーの書き分け方が変わります。

A. 1人のペルソナ（架空データで家計を管理する個人）にまとめる
B. 主ペルソナ（家計を管理する個人）に加え、「キーボードだけで操作する利用者」を別ペルソナとして立てる（おすすめ：キーボード操作の要件をその人の目的として書けるため）
C. 「日々記録する場面」「月末に振り返る場面」「キーボードだけで操作する利用者」の3ペルソナに分ける
X. Other (please specify)

[Answer]: B

## Q2. ストーリーの分け方

ストーリーを何でまとめるかです。後の Unit 分割（独立して進められる単位）の手がかりになります。

A. 機能領域ごと（共通データ契約に関わる土台、収支、カテゴリ、予算、月次集計、CSV 書き出し、CSV 読み込み、横断的な状態表示・キーボード操作）（おすすめ：要件 FR1〜FR9 と1対1に近く、Unit に分けやすいため）
B. 利用の流れごと（初期設定 → 日々の記録 → 月末の振り返り → データの持ち出し・持ち込み）
C. ペルソナごと
X. Other (please specify)

[Answer]: A

## Q3. ストーリーの粒度

1つのストーリーにどこまで含めるかです。

A. 利用者の操作1つにつき1ストーリー（登録、編集、削除などを分ける。全体で20〜30件程度）（おすすめ）
B. 機能ごとに1ストーリー（全体で8〜10件程度。受け入れ条件が多くなる）
C. A よりさらに細かく、正常系と異常系も別ストーリーにする（40件以上）
X. Other (please specify)

[Answer]: A

## Q4. 優先度の付け方

最終的な範囲は Delivery Planning で決めますが、ストーリーの優先度の方針を決めます。

A. ご依頼の4機能（収支登録・カテゴリ別予算・月次集計・CSV 入出力）と、ご依頼で明示された観点（入力エラー・空データ・読み込み中・保存失敗・キーボード操作）に関わるものは Must、それ以外の補助機能（カテゴリ名の変更、重複行の注記など）は Should とする（おすすめ）
B. requirements.md の要件はすべて Must とする
C. 優先度は付けず、Delivery Planning で決める
X. Other (please specify)

[Answer]: A
