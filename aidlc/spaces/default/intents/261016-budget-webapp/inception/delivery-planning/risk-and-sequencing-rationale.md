# 順序の理由と危険の見立て

- Bolt（ボルト）とは、作業の一部を1回で設計から実装・テストまで通し、動くものを仕上げる単位である。
- 採った考え方: **危ないところから（risk-first）**（Q1 = A。Boehm のスパイラルモデルの考え方：不確かさの大きい部分を先に確かめ、その上に積む作業を後にする）。WSJF（「価値＋急ぎ度＋危険度の下げ幅」を大きさで割った値の高い順に作る方法）による点数づけは採らなかった（Q1 で C を選ばなかったため）。
- ウォーキングスケルトン（最初に端から端まで動く細い一本道を作る方式）は採らない（team.md）。

## 1. 順序と理由

| 順 | Bolt / Unit | 理由 |
|----|-------------|------|
| 1 | B1 / U1 data-contract | すべての Unit が依存する土台。ご依頼の「共通データ契約を先に定める」に一致する。CSV の符号化・復号と数式対策もここに含まれるため、最も心配な CSV の扱い（Q4）の核心を最初に確かめられる |
| 2 | B2 / U3 storage | 保存の失敗・利用不可・新しい版の区別と、書き込みの全体取り消しは、外から見えにくい誤りが起きやすい。後の Unit すべての「保存失敗」表示の前提になる |
| 3 | B3 / U4 bookkeeping-core | 収支・カテゴリ・予算をまたぐ規則（使用中の削除拒否、別タブ対策、予算の引き継ぎ）は、要件の中で最も誤りやすい業務規則である |
| 4 | B4 / U5 monthly-summary | U4 の上の純粋な計算。危険は小さいが、集計の一致（FR5.4）をここで確かめておく |
| 5 | B5 / U6 csv-exchange | 不完全な CSV の扱いは心配な点（Q4）だが、核心（符号化・復号）は B1 で確かめ済み。ここでは上限・プレビュー・確定の流れを確かめる |
| 6 | B6 / U2 ui-kit | 依存はないため早く作ることもできるが、データの正しさに比べて危険が小さい。画面（B7）の直前に作り、部品の約束（C6）を画面の実装と近いところで固める |
| 7 | B7 / U7 app-screens | ほかのすべての Unit に依存するため最後。全体をつないだ確認を行う |

## 2. 依存関係との整合

- この順序は、依存関係（U3←U1、U4←U1・U3、U5←U1・U4、U6←U1・U4、U7←U1・U2・U4・U5・U6）をすべて満たす。
- 依存関係だけから決まる順序との違い: U2 はどこにも依存しないため、依存関係上は最初に作ることもできる。今回は危険の大きさで後ろに置いた（上の表の理由）。

## 3. 実行時の順序について

- Construction で実際に Unit を作る順序は、`unit-of-work-dependency.md` の依存関係に基づいて決まる。依存がない U2 は、依存関係の上では U1 と同じく最初に作れるため、実行時の順序がこの計画と異なる場合がある。
- 異なった場合も、依存関係が守られている限り成果物の正しさは変わらない。順序の違いは比較用の記録（`poc-evidence/baseline-serial/run-log.md`）に、実際の順序として残す。

## 4. 危険の一覧

| 危険 | 起こりやすさ | 影響 | 対策 | 確かめる Bolt |
|------|--------------|------|------|----------------|
| CSV の往復で値が変わる（文字コード、引用、改行、数式対策） | 中 | 高 | U1 でテストを先に書き、往復の組み合わせを網羅する | B1、B5 |
| 不正な行や大きなファイルで取り込みが壊れる | 中 | 中 | 上限の事前確認、行単位の検証、全件取り消し | B5 |
| 保存の途中失敗でデータが半端に残る | 低 | 高 | 1回の書き込み処理での全体取り消しと、その失敗テスト | B2、B3 |
| 別タブの操作で規則が破れる（削除済みカテゴリの参照など） | 低 | 中 | 書き込み処理の中での数え直し・存在確認 | B3 |
| 予算の引き継ぎの計算誤り | 中 | 中 | 引き継ぎの例を受け入れ条件どおりにテストする | B3、B4 |
| キーボード操作・読み上げの抜け | 中 | 中 | 部品単位のテスト（B6）と画面のシナリオテスト（B7） | B6、B7 |
| 行カバレッジ 80% に届かない | 低 | 中 | 各 Bolt で Unit ごとに 80% を満たしてから次へ進む | 全 Bolt |
| 契約の不足（Contract Design のレビューで受け入れた指摘） | 中 | 中 | 各 Unit の Functional Design で決め、契約の変更ルールに従って文書とテストを同時に更新する | B3、B5、B6、B7 |
| 開発用パッケージの取得ができない（ネットワーク・権限） | 低 | 高 | 無償の公開パッケージのみを使う。取得できない場合は止めて相談する（有償サービス・認証変更・追加購入はしない） | B1（最初の環境構築） |
