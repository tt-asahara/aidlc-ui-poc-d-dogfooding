## ADR-001: 共通データ契約を独立した部品にする

- **Context**: ご依頼は「共通データ契約を先に定め、独立して進められる Unit と依存関係を整理する」ことを求めている。要件 FR1.4 は画面入力と CSV 読み込みで同じ検証関数を使うことを、FR1.5 は CSV 形式の統一を求めている。
- **Decision**: 型の形・検証規則・CSV の符号化と復号・保存スキーマの版を `DataContract` という、状態を持たずどこにも依存しない部品にまとめる。他のすべての部品はこの部品に依存してよいが、この部品は他に依存しない。
- **Consequences**:
  - 良い点: 契約を最初に完成させれば、持ち主の部品・集計・CSV・画面を契約だけに頼って並べて進められる。純粋な関数なので単独でテストでき、テストを先に書く方針（team.md Testing Posture）と相性がよい。
  - 悪い点: 契約の変更はすべての部品に波及する。そのため契約の変更は慎重に行う必要がある。
  - セキュリティ・コンプライアンス: 入力の検証と CSV の数式対策（NFR8、FR6.3）を1か所で実装でき、抜けが起きにくい。架空データ以外を扱わない制約（C2）には影響しない。
- **Alternatives Rejected**:
  - 層で分ける（Q1 案 B）: 機能をまたいで層が大きくなり、独立して進められる単位を作りにくい。
  - 機能ごとに縦割りし各機能が型を持つ（Q1 案 C）: 画面と CSV で同じ規則を使う要件に対し、規則が重複して食い違う危険がある。

## ADR-002: 部品をまたぐ書き込みを調整役の部品にまとめる

- **Context**: 「使用中のカテゴリは削除できない」（FR3.4）、「削除したカテゴリの予算も消す」（FR3.4）、「別のタブで削除されたカテゴリへの保存は失敗とする」（AC3.4.4）、「CSV の一括追加は全部成功か全部失敗」（FR7.4、NFR4）は、収支・カテゴリ・予算をまたぐ規則である。持ち主の部品同士が直接呼び合うと、カテゴリ↔予算・カテゴリ↔収支で循環依存が生じる。
- **Decision**: 書き込み操作の入り口を `BookkeepingService` に一本化する。この部品は Storage の1回の書き込み処理を開き、その中で最新のデータに対して部品間の規則（カテゴリの存在と種別、使用件数、最後の1件）を確かめてから、持ち主の部品に書き込ませる（Q2 案 A）。持ち主の部品（Ledger、CategoryCatalog、BudgetPlanner）は互いに依存しない。
- **Consequences**:
  - 良い点: 依存関係に循環がない。数えてから消すまでが1回の書き込み処理の中で行われるため、別のタブの操作と食い違わない。部品間の規則が1か所に集まり、テストしやすい。
  - 悪い点: 調整役に操作が集まり、大きくなりやすい。操作ごとに関数を分け、業務の計算（引き継ぎなど）は持ち主の部品に残すことで抑える。
  - セキュリティ・コンプライアンス: 書き込みの入り口が1つになるため、検証を通らない書き込みが起きない。外部送信は行わない（NFR1）。
- **Alternatives Rejected**:
  - 収支・カテゴリ・予算を1つの大きな部品にまとめる（Q2 案 B）: 規則は確かめやすいが、持ち主ごとに独立して進められなくなる。
  - 持ち主同士が直接呼び合う: カテゴリと予算・収支の間で循環依存が生じ、どちらから作るかが決まらない。

## ADR-003: 月次集計は保存せず表示のたびに計算する

- **Context**: 月次集計（FR5）は収支・カテゴリ・予算（引き継ぎを含む）から求まる。集計値と元データが食い違うと信頼が損なわれる（FR5.4）。データ量の想定は最大5,000件（NFR3）。
- **Decision**: `MonthlySummary` はデータを持たず、表示のたびに対象月の収支・カテゴリ・その月に使う予算から計算する（Q3 案 A）。
- **Consequences**:
  - 良い点: 集計値が常に最新で、元データと食い違わない。純粋な計算として単独でテストできる。保存の失敗が集計に波及しない。
  - 悪い点: 表示のたびに計算が走る。5,000件・月単位なら軽いと見込むが、NFR3（500ms 以内）は NFR Requirements で測り方を決めて確かめる。
  - セキュリティ・コンプライアンス: 保存するデータが増えないため、守るべき範囲が広がらない。
- **Alternatives Rejected**:
  - 集計値も保存する（Q3 案 B）: 表示は速いが、収支・予算・カテゴリ名の変更のたびに集計値を正しく更新する必要があり、食い違いの危険がある。

## ADR-004: 保存は IndexedDB を包む部品に閉じ込め、1回の書き込み処理を提供する

- **Context**: 保存先は IndexedDB（要件 Q1）。読み込み中・保存失敗・保存できない環境・新しい版のデータを区別して表示する必要がある（FR8、AC1.2.3）。保存の失敗をテストで再現できる必要がある（AC8.3.1 など）。
- **Decision**: IndexedDB の扱いを `Storage` に閉じ込める。Storage は、データベースの開始と版の確認・移行、複数の保存領域をまとめた1回の書き込み処理（すべて成功かすべて取り消し）、失敗の種類の区別を提供する。他の部品は Storage の窓口だけを使い、IndexedDB を直接扱わない。テストでは同じ窓口を持つ差し替え（失敗させる・遅らせる）を使う。
- **Consequences**:
  - 良い点: 失敗の種類と表示の対応を1か所で決められる。保存の失敗・遅延をテストで起こしやすい。
  - 悪い点: 窓口の設計を誤ると、各持ち主の部品の書き方を縛る。窓口の詳細（関数の形）は Contract Design・Functional Design で決める。
  - セキュリティ・コンプライアンス: データはブラウザ内だけに保存され、外部へ送られない（NFR1、C4）。暗号化はしない（単一利用者・ローカル完結の想定 A1。端末の保護は利用者の端末設定に依存する）。
- **Alternatives Rejected**:
  - 各持ち主の部品が IndexedDB を直接扱う: 失敗の扱いが部品ごとにばらつき、まとめた書き込み処理を作りにくい。
  - localStorage を使う: 要件の Q1 で IndexedDB に決まっている。同期的で、読み込み中の表示を扱う前提と合わない。

## ADR-005: 日付は YYYY-MM-DD の文字入力とし、共通の規則で検証する

- **Context**: モックアップのレビュー（R-01）で、ブラウザ標準の日付入力では存在しない日付（2026-13-01）を打てず、日付のエラー表示（AC2.2.2）とフォーカス移動（AC9.3.2）のテストの前提が合わないと指摘された。CSV 読み込みでも同じ日付の規則を使う（FR1.4）。
- **Decision**: 収支の日付欄は「YYYY-MM-DD」の文字入力にする（Q4 案 A）。存在しない日付は DataContract の規則でエラーにし、画面入力と CSV 読み込みで同じ規則・同じ文言を使う。形式の例（例: 2026-10-16）を入力欄の説明として表示する。
- **Consequences**:
  - 良い点: 画面と CSV で日付の規則が一致し、AC2.2.2・AC9.3.2 をそのままテストできる。ブラウザごとの日付入力の違いに左右されない。キーボードでの入力が単純になる（P2）。
  - 悪い点: 日付選択のカレンダーは標準では出ない。初期値（今日）を入れておき、形式の説明を表示することで入力の手間を抑える。
  - セキュリティ・コンプライアンス: 影響なし（入力は共通の検証を通る）。
  - 下流への影響: refined-mockups の design-system-mapping.md「TransactionForm の `input[type=date]`」は、この決定により「`input[type=text]`（`inputmode` は既定）＋形式の説明」と読み替える。Functional Design で部品の仕様に反映する。
- **Alternatives Rejected**:
  - ブラウザ標準の日付入力（Q4 案 B）: カレンダーが使えるが、画面入力で存在しない日付のエラーが起きず、要件と受け入れ条件のテスト前提が合わない。

## ADR-006: 画面の部品を、見た目の部品と画面の組み立てに分ける

- **Context**: 外部の部品ライブラリは使わず、標準の HTML 要素と自前の CSS で作る（refined-mockups Q4）。アクセシビリティの要件（NFR2、FR9）は、ボタン・入力欄・ダイアログなどの部品の側で満たすのが確実である。
- **Decision**: 業務の知識を持たない見た目の部品を `UiKit`、アプリ枠と5画面の組み立てを `AppScreens` に分ける。UiKit はどこにも依存しない。
- **Consequences**:
  - 良い点: アクセシビリティの振る舞い（フォーカス、読み上げ、エラーの関連づけ）を部品単位でテストでき、画面と別に進められる。
  - 悪い点: 部品の汎用化をしすぎる危険がある。今回の画面に必要な部品（design-system-mapping.md の11種）に限る。
  - セキュリティ・コンプライアンス: 外部のライブラリ・フォント・CDN を使わないため、外部への通信が入り込む余地がない（NFR1）。
- **Alternatives Rejected**:
  - 画面ごとに見た目も作り込む: 部品の重複とアクセシビリティの抜けが起きやすい。
  - 部品ライブラリを使う: refined-mockups の Q4 で採らないと決まっている。

## ADR-007: データの「形の定義」と「持ち主」を分ける

- **Context**: FR1（共通データ契約）は収支・カテゴリ・予算の形を定めることを求める一方、部品の設計では各データの持ち主を1つに決める必要がある。
- **Decision**: データの形（属性名）と規則は DataContract が定め、データの作成・更新・削除と保存は持ち主の部品（Transaction は Ledger、Category は CategoryCatalog、Budget は BudgetPlanner、StorageMeta は Storage）が行う。DataContract はデータを持たない。
- **Consequences**:
  - 良い点: 契約は全部品で共有でき、持ち主は1つに決まる。持ち主以外の部品はデータを書き換えない。
  - 悪い点: 形の変更は契約と持ち主の両方に及ぶ。契約の変更時は持ち主の部品のテストも合わせて更新する。
  - セキュリティ・コンプライアンス: 影響なし。
- **Alternatives Rejected**:
  - DataContract をすべてのデータの持ち主にする: 契約が保存と業務規則を抱えて大きくなり、「先に固めて他を独立に進める」という目的に反する。
