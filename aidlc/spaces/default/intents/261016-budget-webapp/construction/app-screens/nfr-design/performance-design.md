# 性能の設計（app-screens）

- 出典: `construction/app-screens/nfr-requirements/performance-requirements.md`（NFR3 の2つの目標と割り当て）、`construction/app-screens/functional-design/functional-spec.md`（画面の流れ）、`construction/monthly-summary/nfr-design/security-design.md`（U5 の取得）、`construction/csv-exchange/nfr-design/security-design.md`（U6 のプレビューの上限と解析）
- 性能の合格条件は要件（500ms、2 秒）のとおり。ここでは、その条件を満たすための画面の作り方を決める。

## 1. 月次集計の表示の切り替え（500ms）

- 前月・翌月の操作で、読み取りに要求の連番を付け（BR1.4）、最新の要求の結果だけを描画する。古い結果は捨てる。
- 切り替えの間は、前の内容を残したまま「読み込み中」を小さく示す（画面を空にしない）。
- 集計の描画は、支出カテゴリの行（全件）と収入の行だけにする。行数は 30 件程度なので、仮想化はしない。
- 描画に使う再レンダリングは、表示の状態が変わった欄だけに限る（画面全体を作り直さない）。

## 2. CSV の読み込みからプレビューまで（2 秒）

- ファイルの解析（U6）は画面の外で行い、結果を一度だけ描画する。
- プレビューの表示は次のとおり:
  - 取り込める行と取り込めない行は、承認済みの BR7.2 のとおり全件を表示する（件数を絞る「ほか N 行」の表示は使わない。利用者に見える振る舞いを変えないため）。両方とも、一覧は縦にスクロールできる領域に入れる。
  - 最悪のケース（5,000 行がすべて取り込めない行）の描画時間を、Build and Test で測る。合格条件 2 秒を満たさない場合は、この方針を変えるかどうかを利用者に確認する（ここでは上限を入れない）。
  - 件数の上限（5,000 行）は U6 の判定に従う。
- この方針は NFR Requirements の指摘（描画の支配）に対する答え。実ブラウザでの合計は Build and Test で測る。

## 3. 測り方と記録

- **合否の測定手段（本番ビルド、外部から測る）**: 測るのは `npm run build` の成果物を `npm run preview` で配信したページ。測定は Chrome の開発者ツールのパフォーマンス記録（手動）か、ブラウザ操作の道具からページに注入する計時の処理（ページの中の `performance.now()` の差）で行う。計時の処理は dist に含めず、測定の時だけ注入する。
- 操作ごとに、操作の開始（ボタン・矢印の押下）から表示の更新の完了（描画後のフレーム）までを測る。同じ操作を5回行い、中央値で判定し、最悪値も併記する（NFR Requirements の指摘への答え）。
- 測定の前に、架空データを保存領域に入れ、ページを一度読み直す。測定値、実行環境（Chrome のバージョン、OS、CPU）、ビルドの版を Build and Test の記録に残す。
- `src/app/perf.ts`（`import.meta.env.DEV` が真のときだけ記録）は、開発中の目安だけに使う。合否には使わない。本番ビルドでは計測の関数は空になり、dist に計測の印（`perf:`）は残らない（infrastructure-specification 4章で検査する）。
- 本番ビルドの成果物に計測の記録の文字列（`perf:` の印）が残らないことを、Build and Test で確かめる（dist を検索する）。
