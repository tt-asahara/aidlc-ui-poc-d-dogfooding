# 安全性の設計（data-contract）

- 出典: `construction/data-contract/nfr-requirements/security-requirements.md`（NFR1.1、NFR8.1〜NFR8.5）、`construction/data-contract/nfr-requirements/tech-stack-decisions.md`（NFR3.1、NFR5.1、NFR6.1、NFR6.2、NFR9.1）、`construction/data-contract/functional-design/rules.md`、`functional-spec.md`、`inception/contract-design/contract-summary.md`（C1）
- U1 は種類 spec（純粋な関数と型の約束）のため、性能・拡張性・信頼性・監視の設計書は作らない。性能・品質・再現性の目標を満たす手段も、この文書の第5章にまとめる。

## 1. 認証・認可・暗号化

- 対象外。U1 は利用者・保存・通信を持たない（security-requirements.md 第1章）。

## 2. 外部に触れないことの担保（NFR1.1）

| 手段 | 内容 |
|------|------|
| 依存なし | `src/data-contract/` は標準機能（`Intl.Segmenter`、`String.prototype.normalize`、`Number`）と自 Unit のファイルだけを import する。パッケージの import はない |
| Lint で禁止する参照 | `src/data-contract/` に限り、ESLint の `no-restricted-globals`・`no-restricted-properties`・`no-restricted-imports` で次を禁止する: `fetch`、`XMLHttpRequest`、`WebSocket`、`EventSource`、`navigator`、`indexedDB`、`localStorage`、`sessionStorage`、`Worker`、`crypto`、`Date`、`Math.random`、`setTimeout`・`setInterval`、`globalThis`・`window`・`self` 経由の参照、および `node:` で始まる組み込みモジュールの import |
| テストでの確認 | U1 のテストは Node.js 上で実行し、ネットワークを使わない。禁止した参照を書いたファイルで Lint が失敗することを、Lint 設定のテストで1回確かめる |

- 時計と乱数を使わないため、U1 の関数は同じ入力に対して常に同じ結果を返す（日時・id の付与は U4 の責任）。

## 3. 入力の検証の設計（NFR8.2、NFR8.3）

```text
検証関数（入力: unknown を含む値） ─▶ 項目ごとの判定（規則 BR1.x〜BR3.1）
   ├─ 想定外の型 → その項目の required または not-integer として扱う（例外にしない）
   ├─ 全項目を判定（BR1.7）→ エラー一覧
   └─ 結果の型: 成功（正規化した値）／失敗（ValidationError の一覧）
```

- **例外を投げない**: 検証関数の中で起こり得る例外（`normalize` に文字列以外を渡すなど）は、型の確認を先に行うことで起こさない。想定外の例外が起きた場合でも、公開窓口の関数は内部の判定を例外の捕捉で包まず、型の確認で防ぐ（例外を握りつぶさない）。
- **文言は固定**: `ValidationError.message` は規則ごとに定めた固定の文字列（rules.md の violation）だけで、入力値を埋め込まない。文言の一覧はコード上で1つの定数表にまとめ、テストで「全文言に入力値の差し込みがない」ことを確かめる。
- **HTML を作らない**: U1 は文字列の連結で HTML や表示用の書式を作らない。

## 4. CSV の安全な符号化・復号の設計（NFR8.1、NFR8.4）

### 4.1 数式対策の範囲

- 対象の文字は `=` `+` `-` `@`（先頭）と、`'` の直後のこれらと `'`（BR4.5・BR4.6）。
- 先頭のタブ（U+0009）と CR（U+000D）は対象にしない。理由: 保存される値（メモ・カテゴリ名）は BR1.4・BR2.1 で前後の空白（タブ・CR・LF を含む）を取り除いた後の値であり、タブや CR で始まる値は保存されないため。CSV から読み込んだ値も同じ規則で検証してから保存される。
- 対象の列はカテゴリ名とメモだけ。日付・種別・金額は検証済みの決まった形（数字・ハイフン・英字）で、`-` で始まる値（負の金額）は検証で弾かれ、書き出されることがない。

### 4.2 復号の計算量と上限

| 項目 | 設計 |
|------|------|
| 方式 | 入力の文字列を先頭から1回だけ走査する状態機械（「引用の外」「引用の中」「引用の中で直前が `"`」の3状態）。後戻りしないため、時間は入力の長さに比例する |
| 引用が閉じない | 終端に達した時点で、引用が始まった行番号を持つ malformed を返す |
| 時間の上限（NFR3.1、NFR8.4） | 5,000 レコード（約 1MB）の架空 CSV と、1行 1MB の引用付きの値を含む CSV の復号を、それぞれテストで測る。テストの合格条件は 1,000ms 以内（目標 300ms に対し、遅い開発機での揺れを見込んだ余裕）。測定値はテストの出力に記録し、300ms を超えた場合は警告を出す |
| 入力の大きさ | 1MB・5,000 行の上限確認は U6 が復号の前に行う（契約 C5）。U1 は上限を超える入力も同じ方式で処理できる |

### 4.3 往復の保証

- 符号化（BR4.2・BR4.5）と復号（BR4.3・BR4.6）は互いに逆の関係になるよう設計し、次の値の集合で「符号化 → 復号」が元に戻ることをテストする（性質テスト）: 空文字、`'`、`''`、`'abc`、`'=1`、`''=1`、`=`、`=SUM(A1)`、`+1`、`-1`、`@x`、カンマ・ダブルクォート・改行（LF、CRLF）を含む値、200 文字の値、絵文字・結合文字を含む値。

## 5. 性能・品質・再現性の目標を満たす手段

| ID | 手段 |
|----|------|
| NFR3.1 | 4.2 の1回走査の復号と時間測定のテスト |
| NFR5.1 | 金額の判定は「半角数字だけの文字列」を確かめてから `Number` に変換し、`Number.isSafeInteger` と範囲で判定する。数値で渡された値も `Number.isSafeInteger` で判定し、小数・`NaN`・`Infinity` を not-integer とする |
| NFR6.1 | Vitest のカバレッジのしきい値を行 80% に設定する。規則ごとに正常系1つ以上、異常・境界2つ以上のテストを置く（functional-spec.md 第6章の境界値表を使う） |
| NFR6.2 | コード生成の計画で、規則ごとに「テストを書く → 失敗を確かめる → 実装する」の順に手順を並べる |
| NFR9.1 | `package.json` に `"engines": { "node": ">=24 <25" }` を書き、`.nvmrc` に `24` を置く。npm の `engine-strict` を有効にして、範囲外の Node.js での `npm ci` を失敗させる。依存は正確なバージョンで指定し、`package-lock.json` をコミットする |
| NFR8.5 | テストデータの名前と値は「架空」と分かるもの（例: 「架空のランチ」）にする。テストデータの生成関数を1か所にまとめ、実在の固有名詞を使わない |

## 6. 残る危険

| 危険 | 扱い |
|------|------|
| 表計算ソフトの種類によって数式とみなす先頭文字が異なる | 一般的な4文字（= + - @）を対象にする。ほかの先頭文字（全角の＝など）は数式として解釈されない前提とし、Build and Test で表計算ソフトでの確認は行わない（外部ツールのため） |
| 時間測定のテストが遅い環境で不安定になる | 合格条件に余裕（1,000ms）を持たせ、測定値を記録して傾向を見る |
